# Совместные рабочие пространства

Совместный режим включается ссылкой `?workspace=<token>`. Первый запрос к сервису обменивает токен ссылки на HttpOnly cookie `carver_workspace`; сам токен больше не передаётся клиентским API-запросам.

Сервис запускается отдельно от статического Vite-сайта:

```sh
CARVER_ADMIN_SECRET='секрет' CARVER_WORKSPACE_DIR=/var/lib/rezak/workspaces \
  node server/workspace-server.mjs 8787
```

## Админ-панель

`https://<домен>/admin` (Basic Auth, логин/пароль из `CARVER_ADMIN_USER` / `CARVER_ADMIN_PASSWORD`):

- список всех пространств: название, id, число проектов, число активных блокировок, время изменения, ссылка;
- сводка сверху: сколько пространств, сколько проектов всего, сколько открыто сейчас, объём на диске;
- «+ Создать пространство» — новая пустая ссылка;
- «Дублировать» — копия пространства со всеми проектами: **новый URL**, новые id проектов (правки копии не влияют
  на оригинал), ревизии начинаются с 1, блокировки и надгробия не копируются;
- «Удалить» — удаляет файл пространства вместе со всеми его проектами у всех участников (с подтверждением);
- «Копировать» — кладёт в буфер полную ссылку входа.

API под тем же Basic Auth: `GET /admin/workspaces`, `POST /admin/workspaces`, `POST /admin/workspaces/:id/duplicate`,
`DELETE /admin/workspaces/:id`. Тесты: `tests/admin-workspaces.mjs` (API) и `tests/admin-ui.mjs` (кнопки в браузере).

Создание пространства доступно только администратору:

```sh
curl -X POST http://127.0.0.1:8787/admin/workspaces \
  -H 'Authorization: Bearer секрет' -H 'Content-Type: application/json' \
  -d '{"name":"Команда","origin":"https://rezak.example"}'
```

Сервис хранит JSON проектов, транскрипт и историю редактирования; видео, PCM, FileSystemHandle и модели остаются на машинах участников.

Синхронизация двухуровневая: каждые 5 секунд клиент забирает **манифест** (`GET /api/workspace/manifest`, ~1 КБ: id, ревизии, блокировки, надгробия) и скачивает проект (`GET /api/workspace/projects/:id`) только если его ревизия изменилась. Ревизии хранятся в IndexedDB, поэтому перезагрузка страницы обычно стоит одного манифеста. Раньше каждые 5 секунд скачивалось всё пространство (мегабайты), это перегружало канал. Ответы `/api/*` сжимаются gzip (`gzip_proxied any`).

## Локальные проекты и пространства не смешиваются

Проект принадлежит либо этой машине (поля `workspaceId` нет), либо одному пространству. Вкладка, открытая по ссылке
`?workspace=<token>`, показывает только проекты этого пространства; пока идёт первая синхронизация — карточку загрузки,
а не список локальных проектов. Обычная ссылка без токена показывает только локальные проекты. Очередь пакетной
обработки тоже раздельная (`batch-queue-v1:local` и `batch-queue-v1:ws:<id>`), а сохранение отправляет на сервер только
проект, чей `workspaceId` совпадает с пространством вкладки — открыть локальный проект внутри пространства и «залить»
его туда нельзя. Создание проекта во время загрузки пространства отклоняется с подсказкой. Клиенты опрашивают состояние каждые 5 секунд. Редакторская и пакетная блокировки являются арендами на 60 секунд и продлеваются heartbeat-запросами. После закрытия вкладки блокировка освобождается сразу, а при потере связи — максимум через минуту.

`PUT /api/workspace/projects/:id` использует ревизии: устаревшая ревизия получает `409 STALE_REVISION`. `POST /api/workspace/batch/claim` блокирует все проекты очереди одной машины. Для production сервис следует проксировать под тем же HTTPS-origin, что и приложение.

## Удаление проекта

`DELETE /api/workspace/projects/:id` (ровно этот путь) убирает проект из рабочего пространства для всех участников и снимает его блокировки. Освобождение блокировки — `DELETE /api/workspace/projects/:id/lock` — проект не удаляет и надгробия не ставит (это проверяется тестом `tests/workspace-concurrency.mjs`). Клиент спрашивает подтверждение («проект удалится у всех участников») и удаляет локальную копию из IndexedDB вместе с PCM, handle и журналом. Сервер оставляет надгробие (`deleted`), поэтому вкладка со старыми данными не сможет вернуть проект: `PUT` для удалённого id получает `410 PROJECT_DELETED`, и клиент в ответ тоже удаляет проект у себя. Проекты других рабочих пространств и локальные проекты без привязки к пространству не затрагиваются.
